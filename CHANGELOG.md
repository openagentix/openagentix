# Changelog

All notable changes to OpenAgentix are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added
- CI: `hack/ci/green-streak.sh` (issue #196) prints the green runs in a row on `main` for `ci`, `docs`, `e2e` and `e2e-k3s`, for the "30 green runs" exit criterion of release 0.3. It also warns when `e2e` or `e2e-k3s` has no run with event `schedule`: none has been seen yet, and the cause is not known (see `hack/ci/README.md`). Tested offline with fixture run lists (`hack/ci/green-streak-test.sh`).
- Chart: `gateway.serviceType` (issue #165, ADR 0023, part of #31). Default `ClusterIP`; the only other value is `LoadBalancer`, and any other value, an empty one included, fails the render. Reason: agentgateway makes the model gateway's Service a `LoadBalancer`, which is a public IP, a firewall rule and a charge on a managed cloud, and the first GKE run showed it. The chart always renders an `AgentgatewayParameters` object (`<gateway.name>-parameters`, `spec.service.spec.type` only) and points the Gateway at it with `spec.infrastructure.parametersRef`; the standalone `components/model-gateway/manifests/00-gateway.yaml` does the same. Installer: no value is needed; after a remote install, and after a failure once the chart was being applied, it reads the Services and warns about each `LoadBalancer` or `NodePort` one, or says it could not check. Tested with chart render tests (the default and `LoadBalancer` renders differ only in the type), a fake `kubectl` for the check, and a server-side dry run of both objects on a real API server (`hack/ci/apiserver-test.sh`). CI also proves that the Gateway is served on kind and on k3s with the parameters (the `e2e` and `e2e-k3s` jobs pass), and `hack/ci/smoke.sh` reads the live Service `model-gateway` in `agentgateway-system` and checks that `spec.type` is `ClusterIP`. Not proven: the type change of a live `LoadBalancer` Service on a cloud, and the Gateway being `Programmed` (the installer does not wait for it yet; ADR 0023 slices 2 and 3). `ClusterIP` removes the public IP only; any pod in the cluster can still connect.
- Installer: build and push images for a remote cluster (issue #162, ADR 0022, part of #31). With `CLUSTER_TYPE=remote`, `IMAGE_REGISTRY=host[:port]/path` makes `install.sh` push every image it builds to `$IMAGE_REGISTRY/openagentix/<name>:dev-<hash of the source>-<arch>`. A tag already in the registry for `IMAGE_PLATFORM` is reused (`IMAGE_REBUILD=1` builds again); otherwise it runs `docker buildx build --platform $IMAGE_PLATFORM --push --provenance=false --sbom=false --metadata-file`, reads the digest from the metadata file, and checks it in the registry (`imagetools inspect --raw`, and the platform). The chart gets `<path>.image.repository`, `.tag` and `.digest`, so the nodes pull by digest. `IMAGE_PLATFORM` is `linux/amd64` (default) or `linux/arm64`; two platforms are a later step. Before `helm upgrade`, on remote, no platform image may be an unqualified name (which would mean Docker Hub), with `IMAGE_REGISTRY` each must be under it, and a built one must have a digest; images you supply by tag, as in the GKE run, get a warning. The installer never runs `docker login` and never handles a credential: log in first (Artifact Registry: `gcloud auth configure-docker <region>-docker.pkg.dev`); the nodes pull with their own credentials, with no `imagePullSecrets`. Refused before anything changes: `IMAGE_REGISTRY` or `IMAGE_PLATFORM` on kind or k3d, a malformed registry, `ghcr.io/openagentix` (the signed release images), an unknown platform, `CREATE_CLUSTER=1` with remote, images to build on remote without `IMAGE_REGISTRY`, and no `docker buildx` when an image is to be built. `QUICKSTART_BYO=1` now works on remote: the sample goes to `$IMAGE_REGISTRY/openagentix-examples/echo-a2a`, the `AgentDefinition` gets `<repository>@<digest>`, only that prefix is allowed for container agents (a prefix list in your values must name it), and the pull policy stays `Always`; `examples/agents/echo-a2a/Dockerfile` is pinned by digest. New chart value `image.digest` (default empty) under `bridge`, `scheduling`, `gateway.stubModel`, `knowledge.kb`, `notify`, `governance.a2a`, `controlPlane` and `console`, rendered by one helper: `repository:tag@digest`, or `repository@digest` with an empty tag; a bad digest, or an empty tag without a digest, fails the render with the path. The default render is byte-identical. `hack/gke/install.sh` takes `GKE_IMAGES=installer` to use this mode instead of the Cloud Build images. On kind and k3d the installer runs the same commands as before (a golden list in `components/quickstart/tests/golden/`). Tested offline with fake `docker`, `kubectl`, `helm`, `kind` and `k3d` (`hack/ci/images-test.sh`, new cases in `components/quickstart/tests/run.sh`, `hack/gke/tests/run.sh` and the chart tests). The installer has not pushed to a real registry yet, and the buildx output formats are taken from its documentation.
- Chart test (issue #201): every container of every Deployment, StatefulSet and DaemonSet the chart renders (defaults, quick start, minimal, bring your own agent, full demo) must have liveness, readiness and startup probes and CPU and memory requests and limits. The test failed on main for jaeger, victoria-metrics and stub-model (no startup probe) and the Telegram bridge (no readiness or startup probe; the bridge stays on an explicit allowlist until issue #200). Fixed: jaeger, victoria-metrics and stub-model now have a startup probe (2 s period, 30 tries). Those three pods render with one more field; nothing else in the render changes.
- Docs: "Install on GKE" now records the first GKE run (issue #31, 2026-11-26): GKE Standard 1.37.2, one Spot `c3-standard-4`, Dataplane V2; the quick start with the stub model installed in remote mode in 625 s and passed the smoke test (13 checks), the NetworkPolicy test (ingress and egress enforced) and the demo. The images were built by hand in Cloud Build and one manual StorageClass patch was needed; the model gateway Service got a public IP (issue #165). The page has the runbook as run, the IAM grants a new project needs, timings, what was and was not shown, and the teardown. The install page has a table of the clusters where the install was tested and the GKE result for each managed cloud gap.

Tested offline with a fake `gcloud` (`hack/gke/tests/run.sh`); not run against a real project.
- Installer: `SET_DEFAULT_STORAGECLASS=<name>` (part of #31), an opt-in for a cluster that has StorageClasses but no default (GKE 1.37 on the rapid channel ships 10, none default, and the install needs one). Any `CLUSTER_TYPE`; nothing is marked without it. `install.sh` checks the class read-only before anything changes and marks it in step 1 with one `kubectl patch` on `KUBE_CONTEXT`. It refuses, with nothing changed, when the class does not exist or another class is already the default; it does nothing when the class already is the default; it prints what it changed and how to undo it. Run it alone with `KUBE_CONTEXT=<context> hack/default-storageclass.sh [--check] <name>`. With the variable set, the preflight passes the StorageClass check when the class exists and no other is default. Tested with a fake `kubectl` (`hack/ci/default-storageclass-test.sh`, new cases in `components/quickstart/tests/run.sh`); not run on a cluster.
- Installer: new preflight lines (part of #31). A WARN when a Ready node's `node.kubernetes.io/instance-type` starts with `e2-`: Google's Agent Substrate page (<https://docs.cloud.google.com/kubernetes-engine/ai-ml/install-overview-substrate>) asks for GKE Standard with `c3-standard-4` or larger and refuses E2. It is a warning, not a failure, because that page is the only source and it covers Google's path. New INFO lines, not counted in the summary: Spot nodes (`cloud.google.com/gke-spot=true`), whose preemption restarts the install's pods and rebuilds the Substrate golden snapshot; on GKE, that Autopilot is not supported. The preflight does not detect Autopilot: no read-only signal was verified, so the line says how to check it with `gcloud`. Tested with a fake `kubectl`; not run on a cluster. Not changed here: `docs/diary/features/install.md` and `docs/diary/guide/install-gke.md` (another change edits them); their gap rows for the StorageClass default, E2 and Spot can now point at this.
- Installer: `hack/preflight.sh` (issue #168, part of #31). Read-only checks of an existing cluster before anything changes: Kubernetes 1.37 or newer, the `certificates.k8s.io` and `ValidatingAdmissionPolicy` APIs, the Gateway API CRD bundle (1.6.3 or newer), a default StorageClass, node architecture and allocatable CPU and memory, Pod Security labels of the namespaces the installer uses, and whether the context is a local cluster. It prints PASS, WARN or FAIL with a fix for each and exits 1 on a FAIL. The NetworkPolicy line names the dataplane it finds and always warns; it never claims enforcement (`hack/ci/netpol-test.sh` is the live check). `install.sh` runs it for `CLUSTER_TYPE=remote` (`SKIP_PREFLIGHT=1` skips it); run it alone with `KUBE_CONTEXT=<context> hack/preflight.sh`. Tested offline with a fake `kubectl`; not run on a real cluster.
- Installer: the service account issuer for the workload tool server is read from the cluster (issue #167, part of #31): the discovery document, then the kube-apiserver flag, or `SERVICE_ACCOUNT_ISSUER`. It is passed as `controlPlane.containerAgents.serviceAccountTokens.issuer` only when the chart default is what renders and the cluster's issuer differs, so the default render on kind and k3s is unchanged. Tested with JSON fixtures; not run on GKE.
- Docs: messaging audit of the README, the docs home page, the guide pages and the roadmap. The first screen now says who OpenAgentix is for, the problem, what the quick start gives in about 5 minutes (301 to 320 s to the first answer on kind in CI), and links to what works and what does not. Stale claims fixed: bring your own agent is proven in CI on kind (not "planned"), the quick start passed on k3s in CI (not "not tested"), and the old 6 min 34 s figure is replaced. - Installer: `CLUSTER_TYPE=remote` for an existing cluster named by `KUBE_CONTEXT` (issues #161, #163, #164, #169, #170; part of #31). Not run on GKE or any managed cluster; tested offline with fake `kubectl`, `docker`, `helm` and `gcloud`. With `remote`: `KUBE_CONTEXT` is required, a local context name (`kind-*`, `k3d-*`, `docker-desktop` and a few others) is refused unless `ALLOW_LOCAL_CONTEXT=1`, the API server must answer, no cluster is created, `kind` and `k3d` are not needed, and nothing runs on a node (no `docker exec`, no `ctr`). So the quick start does not install on a remote cluster yet. Only its init container is privileged; the container that stays is a non-root, read-only sleep; it tolerates no taint and has no API token. It is not applied by default, is not proven necessary, and `uninstall.sh` deletes its namespace. `components/runtime/up.sh` writes `certificateAuthorityFile` and `discoveryTokenFile` into the Substrate API authentication file only for an in-cluster issuer (`https://kubernetes.default.svc...`); on kind and k3s the file is byte-identical to before. - Console: bring your own agent in the builder (issue #107, umbrella #43). New page `/agents/new/container`, linked from the new agent page when the platform has container agents installed and the policy allows them. It asks for an image (digest required, with an example built from the first allowed registry), a port, plain environment variables, a model from the allowed models and an optional tool profile that is both allowed and opened to container agents. It explains each rule in plain English as you type (tag instead of digest, registry not allowed, port below 1024, reserved or secret-shaped variable), calls the validate route for the draft, and keeps Create off until that check passes. `POST /agents` now runs the same rules for a container definition and answers 422 before it writes anything. `GET /platform` gains `container` (installed, allowed, image prefixes, limit) and `containerAccess` per profile (the workload URL and audience are never sent), and the console reads the profiles from `tools.toolhive.profiles` of the real catalog. `spec.instructions` is no longer sent empty for a container agent. A container agent opens read-only in the builder with its image, and its YAML shows `runtime`. The console's RBAC is unchanged (AgentDefinitions only). Not in this change: resource limits, editing an image after creation, private registries. Limits are in `docs/diary/features/console.md`.
- Docs: "Your first contribution in an hour" (`docs/diary/guide/first-contribution.md`, in the docs sidebar and linked from CONTRIBUTING.md and the README): tools, offline tests without Docker, picking an issue, the DCO sign-off and how to fix a failed DCO check, and what review to expect. `docs/contributing/good-first-issues.md` lists starter tasks that a maintainer can turn into issues.
- Tools for container agents (issue #103, ADR 0019), off by default: `controlPlane.containerAgents.toolProfiles` opens named tool profiles to container agents. Each gets a second vMCP (`<mcp.virtual.name>-<profile>-workload`) with the same tools that accepts only a Kubernetes ServiceAccount token of the workload namespace with its own audience. A container agent with `toolProfile` gets `OPENAGENTIX_MCP_URL`, `OPENAGENTIX_MCP_TOKEN_FILE` (a projected token, one hour, no Secret), the pod label `openagentix.io/tool-profile` and one more egress rule; the admission guard pins all of it. The server accepts only pod-bound tokens of the workload namespace, and two admission policies keep the tool-profile label, projected tokens and token requests in that namespace to the controller's pods (a cluster admin included). A token stays valid until it expires (at most one hour). A profile that is not opened is refused. The quick start with `QUICKSTART_BYO=1` opens `lookup`, and the sample answers `/tools`. With the list empty the chart renders byte-identically to before.
- Console: read-only Schedules and Access pages (issue #5). Schedules lists the chart's schedules from their CronJobs (agent, cron in words, time zone, state, last start) with a detail view; Access lists the A2A gate's caller rules from the ConfigMap `a2a-gate-rules` (caller, who set it, agents, methods, kind of user id rule) with a detail view. Neither shows a prompt, token, key, hash or user id value. New routes `GET /api/v1/schedules` and `GET /api/v1/access` (in the OpenAPI file and the README), new settings `CONSOLE_SCHEDULES_NAMESPACE` and `CONSOLE_GATE_NAMESPACE`. With the console on, the chart adds a Role that may `list` CronJobs in the schedules namespace (only when `schedules` is set) and a Role that may `get` the one ConfigMap `a2a-gate-rules` (only when the gate is on); with the console off the render is unchanged. The Governance page links to Access. Tested offline only, not on a cluster. They read what the chart defines today, not the `Schedule` and `AgentAccess` kinds of ADRs 0016 and 0017.
- Release signing, SBOM and provenance (issue #7, ADR 0018): the release workflow signs every image and the OCI chart with keyless cosign (GitHub OIDC, public Sigstore), makes an SPDX SBOM of each image with syft and attaches it as a cosign attestation, adds SLSA build provenance (`actions/attest-build-provenance`) to the images, the chart and the release files, and attaches the SBOMs (plus an SBOM of the console web app's `pnpm-lock.yaml`), the chart package, the image digest list and a signed `SHA256SUMS` to the GitHub release. Release images are built with no layer cache, with buildx pinned by version and BuildKit and the Dockerfile frontend pinned by digest. Before the release is created, `hack/verify-release.sh` checks all of it, the provenance of each release file included, so a release without a signature, an SBOM or provenance fails. The same script lets users verify (`--tag`, `--checksums`, `--dry-run`); it is tested with a fake cosign and gh (`hack/ci/verify-release-test.sh`, in `make test-shell`). A dry run signs nothing and prints what would be signed. Guide: `docs/diary/guide/verify-release.md`. Not run on a real tag yet. The chart has no SBOM, and the git tag is not signed. Anyone who may push a `v*` tag gets a matching signature until a tag ruleset limits tag creation to maintainers.
- Faster install (issue #29): `install.sh` starts the image builds in the background before the cluster is created, and installs agentgateway and ToolHive while kagent and Substrate are installed (`PREREQS_PARALLEL=0` goes back to one after the other). In CI on a hosted runner the time to the first answer of the quick start with the sample container agent was 301, 306 and 320 s in three runs (runs 45673237057, 45671938772, 45674477495), against 362 to 410 s in five earlier runs. The end wait now covers only the RemoteMCPServers the chart renders, not kagent's built-in ones. New `PROFILE=minimal ./install.sh` (or `--minimal`): the quick start without the console and the bundled observability (`components/quickstart/minimal-values.yaml`); the gate, gateway key and budget, audit lines, tool profile and stub model stay. In the same three runs it took 277 to 316 s without the sample container agent, which is not a clear gain in time over the quick start, with about 100 to 220 MB less memory in use on the runner. `hack/ci/smoke.sh` takes `SMOKE_CONSOLE=0` and `hack/demo.sh` takes `DEMO_CONSOLE=0` for a profile without a console. The `e2e` job runs both profiles. Details and limits in `docs/diary/features/quick-start.md`.
- Demo walkthrough (issue #36): `hack/demo.sh` runs on a quick start install, with no paid key. It creates an `AgentDefinition`, shows its gateway key entry and the token budget (never a key or a hash), asks the agent through the A2A gate, shows the audit line, makes a call the gate must refuse and shows its audit line with the reason, and checks the console API. Each step prints what to look for. It can be run again and removes its definition at the end (`DEMO_KEEP=1` keeps it). Tested offline with a fake `kubectl` (`hack/demo-test.sh`, in `make test-shell`). The `e2e` job runs it after the smoke test. Guide: `docs/diary/guide/demo.md`.
- Time to first working agent, by phase (issue #35): `hack/ci/phases.sh` turns the `install.sh` step log and one `TIMING` line of the smoke test into a table and a JSON file (cluster ready, install done, first agent Ready, first answer, install finished). The `e2e` and `e2e-k3s` jobs print it in the job summary and the log. `install.sh` logs `quick start agent Ready`. Tested offline by `hack/ci/phases-test.sh`. Numbers from seven earlier CI runs are in `docs/diary/features/quick-start.md` with their limits (hosted runner, cold cache, stub model, no clone time).
- Release workflow (issue #6): `.github/workflows/release.yml` runs on a tag `vX.Y.Z`. It fails unless the tag is a semantic version, is on `main` and has a section in `CHANGELOG.md`; runs the pull request checks; pushes each service image to `ghcr.io/openagentix/<name>` with the version tag (linux/amd64) and records the digests; packages the chart with the tag as `version` and `appVersion` and pushes it as an OCI chart; and creates the GitHub release with the changelog section and the image digests as its body. A manual run is a dry run that pushes nothing. `hack/release-notes.sh` builds the body (27 shell checks, `hack/ci/release-notes-test.sh`). Not run on a real tag yet; no SBOM or signatures (issue #7).
- Bring your own agent, slice 4 (issue #104, ADR 0015): a Python sample, `examples/agents/echo-a2a-python`, built with the A2A Python SDK (`a2a-sdk` 1.3.1) and `uvicorn`. It takes the model from `OPENAI_BASE_URL`, `OPENAI_API_KEY` and `OPENAGENTIX_MODEL`, the port from `PORT`, runs as user 65532 with no files written, and pins the base image by digest and every package by hash. Tests: 20 with a fake model plus a contract test against `services/stub-model` (`make test-python-samples`, a new `python-samples` CI job in `ci-ok`). `hack/ci/dockerfiles.sh` also builds a Dockerfile that has the comment line `# ci-build:`. Dependabot watches the pip pins.
- Bring your own agent, slice 2 (issue #102, umbrella #43): `tools/a2a-conform`, a conformance checker for a container agent. `a2a-conform [--fake-model :9099] http://localhost:8080` checks the agent card, its fields and the JSONRPC 1.0 interface, `SendMessage` (message or task, `GetTask`), streaming against the card, the three JSON-RPC error shapes and the port, prints a pass/fail table with a plain-English fix per row, and lists the checks it cannot make (user, read-only root, environment, network) as manual rows. It is a Go module that `hack/ci/go-modules.sh` picks up, so `make test-go` and CI run its tests. New guide page `docs/diary/guide/bring-your-own-agent.md`. - Chart: `platform` (empty by default; `kubernetes` or `openshift`). With `openshift`, no pod pins `runAsUser`, `runAsGroup` or `fsGroup` (the restricted-v2 SCC assigns them), DNS egress goes to `openshift-dns` on port 5353, and `console.route` adds a Route with a NetworkPolicy rule for the router. ### Changed
- CI: the `e2e-k3s` job shows its real result (issue #195). `continue-on-error: true` is removed, so a failed install, smoke test or NetworkPolicy test on k3s is a red check instead of a green one. It is still not in `ci-ok` and not a required check of `main`, so it does not block a merge. Before this, 13 of 23 completed runs had failed while showing green.
- Chart: the model gateway Service is now `ClusterIP` by default (`gateway.serviceType`, ADR 0023). Upgrade note: on upgrade its load balancer is removed. If you reach the model gateway from outside the cluster through it, set `gateway.serviceType: LoadBalancer` before you upgrade, or use `kubectl port-forward`. The default chart render has two more things than in 0.2.0: an `AgentgatewayParameters` object and `spec.infrastructure.parametersRef` on the Gateway.
- `uninstall.sh` names the kube context on every `kubectl` and `helm` call and removes nothing unless that context exists, is the current one after the switch and, with `CLUSTER_TYPE=remote`, its API server answers (issue #169). An unknown `CLUSTER_TYPE` is now refused. It also deletes the namespace `openagentix-node-settings` when present. It never deletes a cluster; on remote it prints the cloud teardown reminder (load balancers and disks first, then the cluster). kind and k3d use the same context as before.
- Container agents, A2A gate: a container agent has 300 s to start its answer, streaming calls included (the body is not timed); `controlPlane.containerAgents.responseTimeoutSeconds` changes it. Each container agent handles 32 calls at once (`maxInFlightPerAgent`), and all container agents together share half of the gate's slots, so the built-in agents keep theirs. The cost: 32 slow calls make one agent answer 503 for every caller until they end. Only `Content-Type`, `Accept`, `A2A-Version`, `A2A-Extensions`, `Traceparent` and `Tracestate` from the caller (plus the gate's own `X-User-Id`) reach a container agent. Only `Content-Type`, `Content-Length`, `Cache-Control`, `Date` and `X-Accel-Buffering` come back from it, plus `X-Content-Type-Options: nosniff`; a redirect from it becomes a 502.
- Container agents: the image is pulled again on every start (`imagePullPolicy: Always`). The chart value `controlPlane.containerAgents.imagePullPolicy` sets it; the quick start uses `IfNotPresent` because its image exists only on the node. Container agents that already run restart once on upgrade, and while the registry is down a restarted agent cannot start.
- Admission guard for container agents: more fields are pinned to what the adapter writes (pull policy, scheduler, termination settings, rollout strategy, probe scheme and timeout, Service cluster IP, session affinity and traffic policy).
- `hack/kind-image-digest.sh` takes the tag that was just loaded as a third argument and uses its digest; on a reused cluster it no longer picks an older image of the same repository.
- Docs: ADR 0015, the README and `what-works.md` now say that DNS lookups can leave the cluster by default, that NetworkPolicy isolation needs a cluster that enforces it, and that the model in a container agent's definition is a hint.

### Fixed
- k3s (`CLUSTER_TYPE=k3d`): the API server now serves the cluster's public ServiceAccount signing keys to callers without a token (#189). k3s starts with `--anonymous-auth=false` unless an authentication config is given, so the workload tool server got HTTP 401 on `/openid/v1/jwks` and refused every token of a container agent. `hack/k3s-authn.yaml` (mounted read-only) allows anonymous access on `/.well-known/openid-configuration` and `/openid/v1/jwks` only; every other path stays closed. A k3d cluster made earlier must be deleted and made again. `e2e-k3s` now checks this (401 on `/api` and `/healthz`, 200 on the keys).
- Installer: `hack/preflight.sh` printed "10 classs" when no StorageClass was default. Counts now read right for 0, 1, 2 and 10 classes ("no StorageClass exists", "1 class, not marked default", "2 classes, none marked default"), and node counts too. Its fix line now names `SET_DEFAULT_STORAGECLASS` and, on GKE (node label `cloud.google.com/gke-nodepool` or a `gce://` provider id) when the class exists, `standard-rwo` (pd-balanced) as the usual choice. Found on a GKE Standard 1.37.2 cluster on the rapid channel, which has 10 classes and none default. Tested with a fake `kubectl`.
- Chart: the kagent controller's NetworkPolicy dropped the controller's own calls on port 8083, so kagent's built-in `RemoteMCPServer` `kagent-api` stayed `Accepted=False` (`DiscoveryFailed`) with a reconciler error every 35 s or so. - The skill registry is a dedicated `openagentix-registry` container on the `kind` docker network. It no longer shares the node's network namespace (which broke after cluster recreation and left a stale container named `ax-registry` looking healthy), and its address is looked up on every run.
- `components/runtime/up.sh` downloads `kubectl-ate` with curl and verifies its SHA-256; no `gh` login is required.
- The missing-allowlist warning in `install.sh` and the README now match the bridge, which refuses to start without `TELEGRAM_ALLOWED_CHAT_IDS`.

### Known issues
- Cold install verified twice from a deleted cluster on one machine with a warm Docker image cache. See "Known limitations" in `README.md`.
